Software Engineering Basics
▼

1.1 What is Software Engineering

Software Engineering is a systematic, disciplined approach to developing, operating, and maintaining software using engineering principles.

Software Engineering ek systematic aur disciplined approach hai jo engineering principles ka use karke software develop, operate, aur maintain karta hai.

Step by step:
1. Gather requirements from the client
2. Design the system architecture
3. Write the code (implementation)
4. Test for bugs and errors
5. Deploy to production
6. Maintain and update over time

1.2 SDLC Phases

SDLC (Software Development Life Cycle) is the process used to plan, design, develop, test, and deploy software.

SDLC (Software Development Life Cycle) wo process hai jo software plan, design, develop, test, aur deploy karne ke liye use hota hai.

Planning

Step by step:
1. Planning: define scope, timeline, budget
2. Analysis: gather and document requirements
3. Design: create architecture and UI mockups
4. Coding: developers write the actual code
5. Testing: QA team verifies correctness
6. Deployment: release to users

1.3 Waterfall Model

Waterfall is a linear model where each phase must finish before the next begins. There is no going back to a previous phase.

Waterfall ek linear model hai jahan har phase pehle complete hona chahiye, tabhi agla start hota hai. Wapas nahi ja sakte.

Requirements
↓
Design
↓
Implementation
↓
Testing
↓
Maintenance
Step by step:
1. Collect all requirements upfront (no changes later)
2. Design entire system on paper
3. Code the whole system
4. Test after coding is done
5. Deploy and maintain

Pros: Simple, well-documented
Cons: No flexibility, testing happens late

1.4 Agile and Scrum

Agile is an iterative approach where software is built in small increments called sprints (2 to 4 weeks). Feedback is collected after each sprint.

Agile ek iterative approach hai jahan software chhote increments (sprints, 2 se 4 weeks) mein banta hai. Har sprint ke baad feedback liya jaata hai.

Step by step (Scrum process):
1. Product Owner creates a backlog of features
2. Team picks items for the sprint (Sprint Planning)
3. Daily Standup: 15-minute sync meeting
4. Team builds and tests during the sprint
5. Sprint Review: demo the work to stakeholders
6. Sprint Retrospective: discuss improvements
7. Repeat for next sprint

2.1 What is UML

UML (Unified Modeling Language) is a standard visual language to represent software design using diagrams.

UML (Unified Modeling Language) ek standard visual language hai jo diagrams ke through software design represent karta hai.

Step by step:
1. UML is NOT a programming language, it is a modeling language
2. Structural diagrams show the static structure (Class, Object, Package)
3. Behavioral diagrams show dynamic behavior (Use Case, Sequence, Activity)
4. Draw diagrams before coding to plan the system

2.2 Use Case Diagram

Use Case Diagram shows what actions a system performs from the user's perspective. Actors are users, use cases are actions.

Use Case Diagram dikhata hai ki system user ke perspective se kya actions perform karta hai. Actors users hain, use cases actions hain.

Library System

Search Book
Borrow Book
Return Book

Actors: Student, Librarian | Use Cases: Search, Borrow, Return

Step by step:
1. Identify actors (who uses the system)
2. Identify use cases (what can they do)
3. Draw system boundary (rectangle)
4. Place actors outside, use cases inside
5. Connect actors to their use cases with lines

3.1 What are Design Patterns

Design Patterns are reusable solutions to common software design problems. They are templates (not actual code). Three categories: Creational, Structural, Behavioral.

Design Patterns common software design problems ke reusable solutions hain. Ye templates hain (actual code nahi). Teen categories: Creational, Structural, Behavioral.

CategoryPurposeExamples
CreationalObject creationSingleton, Factory, Builder
StructuralClass compositionAdapter, Decorator, Facade
BehavioralObject communicationObserver, Strategy, Command

3.2 Singleton Pattern

Singleton ensures only ONE instance of a class exists throughout the application. Useful for loggers, database connections.

Singleton ensure karta hai ki class ka sirf EK instance pure application mein exist kare. Loggers, database connections ke liye useful hai.

Java
class Logger {
    private static Logger instance;        // single instance stored here
    private Logger() { }                    // private constructor blocks new

    public static Logger getInstance() {
        if (instance == null) {
            instance = new Logger();          // create only if not exists
        }
        return instance;
    }

    public void log(String msg) {
        System.out.println("[LOG] " + msg);
    }
}
Step by step (what each line does):
1. private static Logger instance - holds the single object
2. private Logger() - constructor is private so no one can call new Logger()
3. getInstance() - this is the only way to get the object
4. if (instance == null) - checks if object already exists
5. If not, creates one. If yes, returns the same object
6. Result: l1 == l2 will be true (same reference)

3.3 Factory Pattern

Factory Pattern creates objects without exposing creation logic. You ask the factory for an object by type, it gives you the right one.

Factory Pattern objects create karta hai bina creation logic expose kiye. Aap factory se type ke basis pe object maango, wo sahi object de deta hai.

Java
interface Shape {
    void draw();
}
class Circle implements Shape {
    public void draw() { System.out.println("Drawing Circle"); }
}
class Square implements Shape {
    public void draw() { System.out.println("Drawing Square"); }
}
class ShapeFactory {
    Shape create(String type) {
        if (type.equals("circle")) return new Circle();
        if (type.equals("square")) return new Square();
        return null;
    }
}
Step by step:
1. Define a common interface (Shape) with a method draw()
2. Create concrete classes (Circle, Square) that implement Shape
3. ShapeFactory has a create() method that takes a type string
4. Based on the string, it returns the correct object
5. Client never uses "new Circle()" directly, only factory.create("circle")
Try it yourself →

3.4 Observer Pattern

Observer Pattern lets multiple objects (subscribers) listen for changes in another object (publisher). When state changes, all subscribers get notified.

Observer Pattern multiple objects (subscribers) ko ek object (publisher) ke changes sunne deta hai. Jab state change hoti hai, sab subscribers ko notify kiya jaata hai.

Java
interface Observer {
    void update(String msg);
}
class Student implements Observer {
    String name;
    Student(String name) { this.name = name; }
    public void update(String msg) {
        System.out.println(name + " received: " + msg);
    }
}
class Teacher {
    List<Observer> students = new ArrayList<>();
    void subscribe(Observer o) { students.add(o); }
    void notifyAll(String msg) {
        for (Observer o : students) o.update(msg);
    }
}
Step by step:
1. Observer interface has update() method
2. Student implements Observer, prints the message
3. Teacher maintains a list of subscribed students
4. subscribe() adds a student to the list
5. notifyAll() loops through and calls update() on each
6. When teacher posts, every subscribed student gets the message

4.1 Types of Testing

Testing verifies that software works correctly. Different levels target different parts of the system.

Testing verify karta hai ki software sahi kaam karta hai. Alag levels system ke alag parts ko target karte hain.

TypeWhat it testsDone by
Unit TestingIndividual functions/methodsDeveloper
Integration TestingInteraction between modulesDeveloper/Tester
System TestingComplete system end-to-endQA Team
Acceptance TestingDoes it meet user needs?Client
Step by step:
1. Developer writes unit tests for each function
2. Modules are combined and integration tested
3. Full system is tested as a whole
4. Client verifies it meets their requirements

4.2 Black Box vs White Box Testing

Black Box tests inputs and outputs without seeing internal code. White Box tests the internal logic, paths, and branches of code.

Black Box inputs aur outputs test karta hai bina internal code dekhe. White Box code ki internal logic, paths, aur branches test karta hai.

AspectBlack BoxWhite Box
Code visible?NoYes
FocusWhat the system doesHow the system does it
Done byTesterDeveloper
TechniquesEquivalence, BoundaryStatement, Branch coverage
Step by step (Black Box):
1. Look at the requirements (not the code)
2. Create test inputs based on specs
3. Run the system with those inputs
4. Check if output matches expected result
5. You never open the source code
Step by step (White Box):
1. Open the source code and read it
2. Identify all if/else branches
3. Write tests that cover every branch
4. Ensure every line of code runs at least once
5. Check all possible paths through the code

4.3 Test Case Example

A Test Case documents what to test, with what input, and what the expected result should be.

Test Case document karta hai ki kya test karna hai, kaunsa input dena hai, aur expected result kya hona chahiye.

1. Give it a unique ID (TC-01, TC-02...)

SOLID Principles
▼

5.1 S: Single Responsibility Principle

A class should have only ONE reason to change. Each class does one job only.

Ek class ke paas change hone ki sirf EK reason honi chahiye. Har class sirf ek kaam kare.

Java
// BAD: Student class does too many things
class Student {
    void saveToDatabase() { }   // job 1: database
    void generatePDF() { }      // job 2: report
    void sendEmail() { }        // job 3: notification
}

// GOOD: separate classes for separate jobs
class Student { String name; int roll; }
class StudentDB {
    void save(Student s) { System.out.println("Saved " + s.name); }
}
class ReportService {
    void generate(Student s) { System.out.println("PDF for " + s.name); }
}
Step by step (what each line does):
1. BAD version: Student has 3 different jobs (database, PDF, email)
2. If email logic changes, you must modify Student class
3. GOOD version: Student only holds data (name, roll)
4. StudentDB handles saving to database only
5. ReportService handles PDF generation only
6. Now each class has exactly one reason to change

5.2 O: Open/Closed Principle

Classes should be open for extension but closed for modification. Add new features by creating new classes, not changing existing ones.

Classes extension ke liye open honi chahiye lekin modification ke liye closed. Naya feature add karne ke liye nayi class banao, purani mat badlo.

Java
interface Discount {
    double calculate(double price);
}
class RegularDiscount implements Discount {
    public double calculate(double price) { return price * 0.1; }
}
class PremiumDiscount implements Discount {
    public double calculate(double price) { return price * 0.2; }
}
// To add new discount: just create new class, no old code changes
class FestivalDiscount implements Discount {
    public double calculate(double price) { return price * 0.3; }
}
Step by step (what each line does):
1. interface Discount defines the contract: calculate(price)
2. RegularDiscount gives 10% off (price * 0.1)
3. PremiumDiscount gives 20% off (price * 0.2)
4. Need a festival discount? Create FestivalDiscount class
5. No existing class is modified
6. The system is "open" to new discounts, "closed" to edits

5.3 L: Liskov Substitution Principle

A child class should work anywhere the parent class is expected, without breaking the program.

Child class ko parent class ki jagah kahi bhi use kar sakte hain, program break nahi hona chahiye.

Java
class Bird {
    void eat() { System.out.println("Eating"); }
}
class Sparrow extends Bird {
    void fly() { System.out.println("Flying"); }
}

// This works: Sparrow can replace Bird
Bird b = new Sparrow();
b.eat();  // works perfectly

// VIOLATION: Penguin extends Bird but cannot fly
// Solution: separate FlyingBird interface
Step by step (what each line does):
1. Bird is the parent class with eat() method
2. Sparrow extends Bird, adds fly()
3. Bird b = new Sparrow() means we use Sparrow as a Bird
4. b.eat() works because Sparrow inherits eat()
5. If Penguin extended a FlyingBird with fly(), it would break
6. Fix: only give fly() to birds that can actually fly

5.4 I: Interface Segregation Principle

Do not force a class to implement methods it does not need. Use many small interfaces instead of one large one.

Class ko aise methods implement karne pe force mat karo jo wo use nahi karta. Ek badi interface ke bajaye chhoti interfaces use karo.

Java
// BAD: one big interface
interface Worker {
    void work();
    void eat();
    void sleep();
}

// GOOD: small focused interfaces
interface Workable { void work(); }
interface Eatable  { void eat(); }

class Robot implements Workable {
    public void work() { System.out.println("Robot working"); }
}
class Human implements Workable, Eatable {
    public void work() { System.out.println("Human working"); }
    public void eat() { System.out.println("Human eating"); }
}
Step by step (what each line does):
1. BAD: Worker forces eat() and sleep() on every implementor
2. Robot does not eat or sleep, but is forced to implement them
3. GOOD: split into Workable and Eatable
4. Robot implements only Workable (it only works)
5. Human implements both Workable and Eatable
6. No class is forced to have useless methods

5.5 D: Dependency Inversion Principle

High-level modules should not depend on low-level modules. Both should depend on abstractions (interfaces).

High-level modules ko low-level modules pe depend nahi karna chahiye. Dono ko abstractions (interfaces) pe depend karna chahiye.

Java
// Abstraction (interface)
interface Database {
    void save(String data);
}

// Low-level modules
class MySQL implements Database {
    public void save(String data) {
        System.out.println("MySQL: " + data);
    }
}
class MongoDB implements Database {
    public void save(String data) {
        System.out.println("Mongo: " + data);
    }
}

// High-level module depends on interface, not class
class UserService {
    Database db;
    UserService(Database db) { this.db = db; }
    void createUser(String name) { db.save(name); }
}
Step by step (what each line does):
1. interface Database is the abstraction with save()
2. MySQL and MongoDB are low-level (concrete) implementations
3. UserService is the high-level module (business logic)
4. UserService takes Database in its constructor (not MySQL directly)
5. You can pass MySQL or MongoDB, both work
6. To switch databases, just pass a different object. No code change in UserService
