1. What is Software Engineering

Software Engineering is the systematic approach to developing, operating, and maintaining software. It applies engineering principles to software development.

Software Engineering software develop, operate, aur maintain karne ka systematic approach hai. Ye engineering principles ko software development mein apply karta hai.

2. SDLC (Software Development Life Cycle)

3. Waterfall Model

Waterfall is a linear, sequential model. Each phase must be completed before the next one starts. No going back.

Waterfall ek linear, sequential model hai. Har phase pehle complete hona chahiye, tabhi agla phase start hota hai. Wapas nahi ja sakte.

Advantages: Simple, easy to manage, clear documentation.
Disadvantages: No flexibility, late testing, not suitable for changing requirements.

Advantages: Simple, manage karna easy, clear documentation.
Disadvantages: Flexibility nahi, testing late hoti hai, changing requirements ke liye suitable nahi.

4. Agile and Scrum

Agile is an iterative approach. Software is developed in small parts called sprints (2-4 weeks). Customer feedback is taken after each sprint.

Agile ek iterative approach hai. Software chhote parts mein develop hota hai jise sprints kehte hain (2-4 weeks). Har sprint ke baad customer feedback liya jaata hai.

Scrum Roles:
- Product Owner: decides what to build
- Scrum Master: removes obstacles, manages process
- Team: developers who build the product

Scrum Events:
- Sprint Planning: decide sprint goals
- Daily Standup: 15-minute daily meeting
- Sprint Review: demo to stakeholders
- Sprint Retrospective: what went well, what to improve

5. Requirements (Functional vs Non-Functional)

Functional requirements define what the system should do. Non-functional requirements define how it should perform.

Functional requirements define karti hain ki system kya karega. Non-functional requirements define karti hain ki system kaise perform karega.

FunctionalNon-Functional

System sends emailSystem handles 1000 users at a time
Add items to cartSystem must be available 99.9% of time
Generate reportData must be encrypted

1. What is UML

UML (Unified Modeling Language) is a standard way to visualize software design. It uses diagrams to show structure and behavior of a system.

UML (Unified Modeling Language) software design ko visualize karne ka standard tarika hai. Ye diagrams use karta hai system ki structure aur behavior dikhane ke liye.

Types of UML Diagrams:
Structural: Class Diagram, Object Diagram, Package Diagram
Behavioral: Use Case, Sequence, State, Activity Diagram

2. Use Case Diagram

Use Case Diagram shows what a system does from the user's point of view. It has actors (users) and use cases (actions).

Use Case Diagram dikhata hai ki system user ke point of view se kya karta hai. Ismein actors (users) aur use cases (actions) hote hain.

Elements:
- Actor: stick figure (external user or system)
- Use Case: oval (an action the system performs)
- System Boundary: rectangle around use cases
- Relationships: include, extend, generalization

1. What are Design Patterns

Design Patterns are proven solutions to common software design problems. They are templates, not code. There are 3 types: Creational, Structural, and Behavioral.

Design Patterns common software design problems ke proven solutions hain. Ye templates hain, code nahi. 3 types hain: Creational, Structural, aur Behavioral.

TypePurposeExamples
CreationalObject creationSingleton, Factory, Builder
StructuralClass compositionAdapter, Decorator, Facade
BehavioralObject interactionObserver, Strategy, Command

2. Singleton Pattern

Singleton ensures only one instance of a class exists. Useful for database connections, loggers, and configuration.

Singleton ensure karta hai ki class ka sirf ek instance ho. Database connections, loggers, aur configuration ke liye useful hai.

Java Code: 
class Logger {
    private static Logger instance;
    private Logger() { }

    public static Logger getInstance() {
        if (instance == null) {
            instance = new Logger();
        }
        return instance;
    }

    public void log(String msg) {
        System.out.println("[LOG] " + msg);
    }
}

public class Main {
    public static void main(String[] args) {
        Logger l1 = Logger.getInstance();
        Logger l2 = Logger.getInstance();
        l1.log("Server started");
        System.out.println(l1 == l2);  // true, same object
    }
}
Output:
[LOG] Server started
true

3. Factory Pattern

Factory pattern creates objects without exposing creation logic. The client uses a factory method instead of "new".

Factory pattern objects banata hai bina creation logic expose kiye. Client "new" ke bajaye factory method use karta hai.

Java Code: 
interface Notification {
    void send(String message);
}

class EmailNotification implements Notification {
    public void send(String message) {
        System.out.println("Email: " + message);
    }
}

class SMSNotification implements Notification {
    public void send(String message) {
        System.out.println("SMS: " + message);
    }
}

class NotificationFactory {
    public Notification create(String type) {
        if (type.equals("email")) return new EmailNotification();
        if (type.equals("sms")) return new SMSNotification();
        return null;
    }
}

public class Main {
    public static void main(String[] args) {
        NotificationFactory factory = new NotificationFactory();
        Notification n = factory.create("email");
        n.send("Hello!");
    }
}
Output:
Email: Hello!

4. Observer Pattern

Observer pattern lets objects subscribe to events. When state changes, all subscribers are notified automatically.

Observer pattern objects ko events subscribe karne deta hai. Jab state change hoti hai, sab subscribers ko automatically notify kiya jaata hai.

Java Code: 
import java.util.ArrayList;
import java.util.List;

interface Observer {
    void update(String message);
}

class Student implements Observer {
    String name;
    Student(String name) { this.name = name; }
    public void update(String message) {
        System.out.println(name + " received: " + message);
    }
}

class Teacher {
    List<Observer> students = new ArrayList<>();

    void subscribe(Observer o) { students.add(o); }

    void notifyAll(String msg) {
        for (Observer o : students) {
            o.update(msg);
        }
    }
}

public class Main {
    public static void main(String[] args) {
        Teacher t = new Teacher();
        t.subscribe(new Student("Rahul"));
        t.subscribe(new Student("Priya"));
        t.notifyAll("Assignment due tomorrow!");
    }
}
Output:
Rahul received: Assignment due tomorrow!
Priya received: Assignment due tomorrow!

5. Strategy Pattern

Strategy pattern lets you choose an algorithm at runtime. You define a family of algorithms and make them interchangeable.

Strategy pattern runtime pe algorithm choose karne deta hai. Aap algorithms ka ek family define karte ho aur unhe interchangeable banate ho.

Java Code: 
interface SortStrategy {
    void sort(int[] arr);
}

class BubbleSort implements SortStrategy {
    public void sort(int[] arr) {
        System.out.println("Sorting with Bubble Sort");
        // bubble sort logic here
    }
}

class QuickSort implements SortStrategy {
    public void sort(int[] arr) {
        System.out.println("Sorting with Quick Sort");
        // quick sort logic here
    }
}

class Sorter {
    private SortStrategy strategy;

    void setStrategy(SortStrategy s) {
        this.strategy = s;
    }

    void sort(int[] arr) {
        strategy.sort(arr);
    }
}

public class Main {
    public static void main(String[] args) {
        Sorter sorter = new Sorter();
        int[] data = {5, 2, 8, 1};

        sorter.setStrategy(new BubbleSort());
        sorter.sort(data);

        sorter.setStrategy(new QuickSort());
        sorter.sort(data);
    }
}
Output:
Sorting with Bubble Sort
Sorting with Quick Sort

Software Testing
▼

1. Types of Testing

Testing verifies that software works correctly. There are different levels of testing.

Testing verify karta hai ki software sahi kaam kar raha hai. Testing ke alag-alag levels hote hain.

TypeWhat it testsDone by
Unit TestingIndividual methods or functionsDeveloper
Integration TestingInteraction between modulesDeveloper/Tester
System TestingComplete system end-to-endTesting Team
Acceptance TestingDoes it meet user requirements?Client/User

2. Black Box Testing

Black Box Testing tests the software without looking at internal code. You only check inputs and expected outputs.

Black Box Testing software ko bina internal code dekhe test karta hai. Sirf inputs aur expected outputs check karte hain.

Techniques:
- Equivalence Partitioning: divide inputs into valid/invalid groups
- Boundary Value Analysis: test at boundaries (min, max, min-1, max+1)
- Decision Table: test combinations of conditions
Example: 
// Testing a login function (black box)
// We do NOT look at the code inside

// Test Case 1: Valid credentials
Input: username="admin", password="1234"
Expected: Login successful

// Test Case 2: Wrong password
Input: username="admin", password="wrong"
Expected: Invalid password

// Test Case 3: Empty fields
Input: username="", password=""
Expected: Fields cannot be empty

3. White Box Testing

White Box Testing tests the internal logic of the code. You check paths, branches, and conditions inside the code.

White Box Testing code ki internal logic test karta hai. Code ke andar paths, branches, aur conditions check karte hain.

Techniques:
- Statement Coverage: every line executes at least once
- Branch Coverage: every if/else branch is tested
- Path Coverage: every possible path through code is tested
Example: 
// Code to test
int getDiscount(int amount) {
    if (amount > 1000) {
        return 20;   // Path 1
    } else {
        return 5;    // Path 2
    }
}

// White box tests (we know the code):
// Test 1: amount = 1500 (takes Path 1, returns 20)
// Test 2: amount = 500  (takes Path 2, returns 5)
// Both branches covered!

4. Test Case

A test case is a set of conditions to check if a feature works correctly. It has ID, description, input, expected output, and status.

Test case conditions ka set hai jo check karta hai ki feature sahi kaam kar raha hai. Ismein ID, description, input, expected output, aur status hota hai.

5. JUnit Basics

JUnit is a testing framework for Java. You write test methods with @Test annotation. Use assertions to check results.

JUnit Java ke liye ek testing framework hai. @Test annotation ke saath test methods likhte hain. Assertions se results check karte hain.

Annotations:
@Test - marks a test method
@BeforeEach - runs before each test
@AfterEach - runs after each test

Assertions:
assertEquals(expected, actual)
assertTrue(condition)
assertFalse(condition)
assertNull(object)
Java Code: 
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class Calculator {
    int add(int a, int b) { return a + b; }
    int divide(int a, int b) { return a / b; }
}

class CalculatorTest {
    Calculator calc = new Calculator();

    @Test
    void testAdd() {
        assertEquals(5, calc.add(2, 3));
        assertEquals(0, calc.add(-1, 1));
    }

    @Test
    void testDivide() {
        assertEquals(5, calc.divide(10, 2));
        assertThrows(ArithmeticException.class,
            () -> calc.divide(10, 0));
    }
}
Output:
All tests passed (2 tests)

SOLID Principles
▼

1. S: Single Responsibility Principle

A class should have only one reason to change. One class, one job.

Ek class ko change karne ki sirf ek reason honi chahiye. Ek class, ek kaam.

Java Code: 
// BAD: One class doing multiple jobs
class Student {
    void saveToDatabase() { }
    void generateReport() { }
    void sendEmail() { }
}

// GOOD: Each class has one job
class Student {
    String name;
    int roll;
}

class StudentRepository {
    void save(Student s) {
        System.out.println("Saved " + s.name);
    }
}

class ReportGenerator {
    void generate(Student s) {
        System.out.println("Report for " + s.name);
    }
}

2. O: Open/Closed Principle

A class should be open for extension but closed for modification. Add new features by adding new code, not changing existing code.

Class extension ke liye open honi chahiye, modification ke liye closed. Naya feature add karo naya code likh ke, purana code change mat karo.

Java Code: 
// Open for extension using interface
interface Discount {
    double calculate(double price);
}

class RegularDiscount implements Discount {
    public double calculate(double price) {
        return price * 0.1;
    }
}

class PremiumDiscount implements Discount {
    public double calculate(double price) {
        return price * 0.2;
    }
}

// Adding new discount = new class, no change to existing code
class FestivalDiscount implements Discount {
    public double calculate(double price) {
        return price * 0.3;
    }
}

3. L: Liskov Substitution Principle

A child class should be usable wherever the parent class is used, without breaking the program.

Child class ko parent class ki jagah use karna chahiye bina program tode.

Java Code: 
// GOOD: Child works wherever parent is expected
class Bird {
    void eat() { System.out.println("Eating"); }
}

class Sparrow extends Bird {
    void fly() { System.out.println("Flying"); }
}

// This works fine:
Bird b = new Sparrow();
b.eat();  // works perfectly

// BAD example: Penguin extends Bird with fly()
// Penguin cannot fly, so it violates LSP
// Solution: separate FlyingBird from Bird

4. I: Interface Segregation Principle

Do not force a class to implement methods it does not use. Use many small interfaces instead of one big interface.

Class ko aise methods implement karne par force mat karo jo wo use nahi karta. Ek badi interface ke bajaye bahut si chhoti interfaces use karo.

Java Code: 
// BAD: One big interface
interface Worker {
    void work();
    void eat();
    void sleep();
}

// GOOD: Small, focused interfaces
interface Workable {
    void work();
}

interface Eatable {
    void eat();
}

class Robot implements Workable {
    public void work() {
        System.out.println("Robot working");
    }
    // Robot does not need eat() or sleep()
}

class Human implements Workable, Eatable {
    public void work() { System.out.println("Human working"); }
    public void eat() { System.out.println("Human eating"); }
}

5. D: Dependency Inversion Principle

High-level modules should not depend on low-level modules. Both should depend on abstractions (interfaces).

High-level modules ko low-level modules pe depend nahi karna chahiye. Dono ko abstractions (interfaces) pe depend karna chahiye.

Java Code: 
// BAD: High-level depends on low-level
class MySQLDatabase {
    void save(String data) { }
}

class UserService {
    MySQLDatabase db = new MySQLDatabase(); // tightly coupled
}

// GOOD: Both depend on abstraction
interface Database {
    void save(String data);
}

class MySQLDatabase implements Database {
    public void save(String data) {
        System.out.println("Saved to MySQL: " + data);
    }
}

class MongoDB implements Database {
    public void save(String data) {
        System.out.println("Saved to MongoDB: " + data);
    }
}

class UserService {
    Database db;

    UserService(Database db) {
        this.db = db;  // depends on interface, not class
    }

    void createUser(String name) {
        db.save(name);
    }
}

public class Main {
    public static void main(String[] args) {
        Database db = new MongoDB();
        UserService service = new UserService(db);
        service.createUser("Rahul");
    }
}
Output:
Saved to MongoDB: Rahul
