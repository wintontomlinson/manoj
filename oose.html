What is UML?

UML (Unified Modeling Language) is a standard notation for visualizing software design. It has Structural Diagrams (Class, Object, Package) and Behavioral Diagrams (Use Case, Sequence, Activity, State).

1. Use Case Diagram

Shows the interaction between actors (users/external systems) and use cases (system functions). Used to capture functional requirements.

What are Design Patterns?

Design patterns are reusable solutions to common software design problems. They were documented by the "Gang of Four" (GoF) and are categorized into three types:

CategoryPurposePatterns
CreationalObject creation mechanismsSingleton, Factory, Builder, Prototype
StructuralClass/object compositionAdapter, Decorator, Facade, Proxy
BehavioralObject interaction/communicationObserver, Strategy, Command, Iterator

Singleton Pattern (Creational)

Ensures a class has only one instance and provides a global access point. Used for: Database connections, Logger, Configuration manager.

Java 
// Singleton Pattern
public class Database {
    private static Database instance;

    private Database() {
        // Private constructor prevents external instantiation
    }

    public static synchronized Database getInstance() {
        if (instance == null) {
            instance = new Database();
        }
        return instance;
    }

    public void query(String sql) {
        System.out.println("Executing: " + sql);
    }
}

Factory Pattern (Creational)

Provides an interface for creating objects without specifying the exact class. The factory method decides which class to instantiate.

Observer Pattern (Behavioral)

Defines a one-to-many dependency between objects. When one object (subject) changes state, all dependents (observers) are notified automatically.

Java 
// Observer Pattern
interface Observer {
    void update(String message);
}

class NotificationService {
    private List<Observer> observers = new ArrayList<>();

    public void subscribe(Observer o) { observers.add(o); }
    public void unsubscribe(Observer o) { observers.remove(o); }

    public void notify(String msg) {
        for (Observer o : observers) {
            o.update(msg);
        }
    }
}

class Student implements Observer {
    private String name;
    Student(String n) { name = n; }

    public void update(String msg) {
        System.out.println(name + " received: " + msg);
    }
}

Strategy Pattern (Behavioral)

Defines a family of algorithms, encapsulates each one, and makes them interchangeable. The strategy can be selected at runtime.

SOLID Principles

SOLID is a set of five design principles that help developers write maintainable, scalable, and flexible object-oriented software. Introduced by Robert C. Martin (Uncle Bob).

S
Single Responsibility Principle
"A class should have only one reason to change." Each class should do ONE thing and do it well.
Java 
// BAD - Multiple responsibilities
class Student {
    void saveToDatabase() { }
    void generateReport() { }
    void sendEmail() { }
}

// GOOD - Single responsibility each
class Student { /* only student data */ }
class StudentRepository { void save(Student s) { } }
class ReportGenerator { void generate(Student s) { } }
class EmailService { void send(String to) { } }
O
Open/Closed Principle
"Software entities should be open for extension but closed for modification." Add new features by extending, not changing existing code.
Java 
// Open for extension via interface
interface DiscountStrategy {
    double calculate(double price);
}

class StudentDiscount implements DiscountStrategy {
    public double calculate(double price) {
        return price * 0.8;  // 20% off
    }
}

class FacultyDiscount implements DiscountStrategy {
    public double calculate(double price) {
        return price * 0.7;  // 30% off
    }
}
L
Liskov Substitution Principle
"Objects of a superclass should be replaceable with objects of a subclass without breaking the application." Child classes must not violate parent class behavior.
I
Interface Segregation Principle
"No client should be forced to depend on methods it does not use." Create specific, focused interfaces instead of one large interface.
Java 
// BAD - Fat interface
interface Worker {
    void code();
    void test();
    void design();
    void manage();
}

// GOOD - Segregated interfaces
interface Coder { void code(); }
interface Tester { void test(); }
interface Designer { void design(); }

class Developer implements Coder, Tester {
    public void code() { /* ... */ }
    public void test() { /* ... */ }
}
D
Dependency Inversion Principle
"High-level modules should not depend on low-level modules. Both should depend on abstractions." Program to interfaces, not implementations.
Java 
// Depend on abstraction, not concrete class
interface MessageSender {
    void send(String message);
}

class EmailSender implements MessageSender {
    public void send(String msg) {
        System.out.println("Email: " + msg);
    }
}

class NotificationService {
    private MessageSender sender;  // Depends on interface

    NotificationService(MessageSender sender) {
        this.sender = sender;
    }

    void notify(String msg) {
        sender.send(msg);
    }
}
